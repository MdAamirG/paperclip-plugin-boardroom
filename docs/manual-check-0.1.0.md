## Follow-ups

Severity: blocker, major, minor.

- **F1 (blocker): host calls made from a live session event callback are refused, so a multi-Turn Round does not continue.** Cause found in host `server/src/services/plugin-worker-manager.ts` (`contextForWorkerMessage`): a worker call made outside a host invocation (the `onEvent` callback of `ctx.agents.sessions.send`, run by `handleSessionEvent`) is only admitted for a company that has a plugin configuration row (`proactiveCompanyScopes`). Boardroom has no settings, so no row exists. Effects without the row: the next Turn's `agents.sessions.create` fails and the Turn is recorded as skipped `not_invokable` (step 5 first attempt, Turn `b90f9e31-f6d2-4597-ab94-32fc3d216568`); `activity.log`, `agents.sessions.close` and `streams.emit` fail ("missing, expired, or unknown invocation scope"), so Turn and Round-completion activity entries are lost and sessions are not closed. Workaround that worked: save an empty per-company config (`POST /api/plugins/:id/config {companyId, configJson: {}}`). The plugin needs either to make these calls inside an invocation (for example settle from `ctx.events.on` handlers, whose invocation carries the company) or to document and automate the config row. The automated harness does not model this host gate.
  **Status: fixed in branch `fix-manual-check-findings` (needs re-check on a real host). Why this approach: the SDK gives a plugin no way to save its own configuration row, and a live callback cannot be bound to the invocation that started it (that invocation has ended and the host forgets it), so the plugin must not depend on out-of-invocation calls. Settling is now two steps. `settleTurn` saves the outcome and the reply Message (database only, which the host does not gate) and marks the Turn `host_pending` (migration 002). `finalizeTurn` does the host part once (activity entry, `sessions.close`, stream, advancing the Round), claimed through `host_pending`, and only when a cheap probe (`agents.list`) shows the host accepts calls from the current context. Contexts the host accepts, which finish pending work: the `agent.run.*` event handlers (the invocation carries the event's company), any `GET /rooms/:id/rounds` (the page polls it, F5), and the sweep for a company that has a config row. The harness now models the host rule (`tests/support/host/invocation.ts`; `tests/api/invocation-scope.spec.ts` fails without the fix). Remaining dependency: Turn 2 starts when the host delivers `agent.run.finished` for Turn 1 (or the page polls); `agent.run.finished` was not isolated in this check, so confirm it on a real host. With no event and no open page, a Round in a company without a config row waits until one of them happens.**
  **Re-check 2026-10-10 (plugin `aabb181`): not fixed for a posted reply.** With no page open and no config row, Round 1 stopped after Turn 1 for 7 minutes and Turn 2 started only when `GET /rooms/:id/rounds` was called. The `agent.run.finished` handler runs, but always while the live callback is still saving the reply, so it finds nothing it may finalize, and the live callback's own attempt is refused. See F9. The database half works: replies were saved, and Turn and Round-completion entries and session closes all happened once a request finished the host part. The fix is under F9 (branch `fix-f9-posted-turn-stall`).

- **F9 (blocker): the run event handler never finishes a posted Turn, so with no page open a Round without a config row stops after every posted reply.** For every succeeded run the host first sends the live `done` (`heartbeat.ts` publishes `heartbeat.run.status` before `publishRunLifecyclePluginEvent`, lines 12776 to 12781), then `agent.run.finished`. The worker handles both together. In the `done` path, `settleTurn` (`src/engine/rounds.ts:294`) marks the Turn `finished` + `host_pending` and then saves and links the Message over several host round trips. The `agent.run.finished` handler (`src/engine/recovery.ts:69-73`) reads the Turn during that gap. It is no longer `running`, so the handler calls `finishPendingHostWork`. That returns at `src/engine/rounds.ts:396` without doing anything: `listUnfinalizedTurns` skips a posted Turn with no Message (`src/db/turns.ts:285`), and `listIdleRunningRounds` skips a Round with a `host_pending` Turn (`src/db/runs.ts:65`). The `done` path then calls `finalizeTurn`, whose probe is refused (`src/engine/rounds.ts:350`; the host's `agents.sessions.event` notification carries no company, so it has no invocation). After that, nothing inside an invocation comes back, and the sweep is refused too. Evidence: 4 of 4 posted Turns stayed `host_pending` (runs `51d21ba1`, `2417284f`, `36e88a64`, `3e387ac9`), each with one host refusal logged at the moment the Turn finished. By contrast, the cancelled Gemini Turn (no Message to wait for) was finished by the run event handler within 30 ms with no page open. Possible fixes: have the run event handler wait for or retry the Message link, or do the Message save inside the run event handler (from `heartbeat_runs.result_json.summary`) when the live path has not linked it yet.
  **Status: fixed in branch `fix-f9-posted-turn-stall` (needs re-check on a real host). The run event handler now waits for the live settlement before it does the host part. Each settlement registers itself in the worker while it runs (`settleTurn` in `src/engine/rounds.ts`). When the handler finds the Turn already settled, or loses the settle-once claim to the live event, it waits for that settlement to end (at most 60 s). If the Turn is still `posted` with no Message linked (a settlement this worker cannot see), it polls for the link (at most 10 s). Then it calls `finishPendingHostWork` inside its own invocation, which writes the activity entry, closes the session and starts the next Turn. The wait is safe because the host delivers an event to the worker as a notification whose invocation scope lasts 15 minutes and does not end when the handler returns or replies (host `server/src/services/plugin-worker-manager.ts`: `notify` registers the scope with `MAX_RPC_TIMEOUT_MS`, lines 3462 to 3466; the constant is 15 minutes, line 85; event delivery calls `notifyWorker("onEvent")` in `plugin-host-services.ts:1569`). The SDK runs the handler and every continuation inside that scope (`worker-rpc-host.ts:2271`). Tests: `tests/api/invocation-scope.spec.ts`, "a run event that arrives while the live settlement is still saving the reply (F9)". They fail without the fix. Still open: if the worker dies after a Turn is marked `posted` and before its Message is linked, the sweep repairs the link after 120 s, but in a company without a config row the host part still waits for a later run event or a page request.**
